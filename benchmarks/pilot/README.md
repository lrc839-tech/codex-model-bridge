# 三组配对小试验

这个目录只记录和汇总**真实测量**，不会调用模型。现在没有试验结果，不能据此宣称节省 Token 或质量更高。

## 怎么测

1. 先准备 6 个未给模型看过答案的小任务，覆盖局部 bug、跨文件修改、多项明确约束和原因定位等，每组重复 2 次（共 36 次运行），先检查测量方法；有方向后扩大到 20–30 个不同任务。不要把首轮小样本当正式效果证明。预先冻结任务、代码起点、隐藏测试、时间上限和人工介入规则。公开测试可给执行者，隐藏测试只由统一验收脚本运行。
2. 每个任务从同一份干净代码开始，分别运行下面三组，打乱执行顺序。每组至少重复 2 次。固定执行模型、工具权限、联网范围、时间/Token 上限；记录 Codex/DS 模型及版本、Harness 版本和设置（另存试验说明，不放 Key）。
   - `codex_only`：桌面 Codex 规划、执行、验收。
   - `codex_ds_bridge`：桌面 Codex 规划，Bridge 分配 DS 执行及初审，Codex 最终决策。
   - `dsh_ds`：官方 [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) 与同一 DS 模型，独立完成相同任务。
   - 可选 `ds_only_same_bridge`：同一 Bridge 工具和任务，仅用 DS 规划、执行、验收；用来区分规划模型的贡献与 Harness 的贡献。
3. 导出各方真实 usage，填 `runs-template.csv`。**一行是一组任务的一次完整尝试**，包括所有内部修复、重试、验收、Codex 回退与最终回答。任务没有完成也必须保留该行。不要把中间调用拆成独立样本。
4. 统一运行隐藏验收，记录是否全部通过、是否需要人工返工。先看质量，再比较 Token、费用和耗时。

## 正式实验前的采集前置条件

当前发布版在执行正常返回、或复审 schema 验证之后才保存用量；异常路径可能漏掉已经消耗的 usage。正式对照前应先改成**每个请求一返回就追加 ledger**，即使后续解析失败或任务超时，也保留该次用量与请求状态。服务端未返回用量时明确标记 `unknown`，汇总行不能标为 usage 完整。对调用次数、usage、重试和回退做账，不能只读取成功的最终结果文件。

用 fresh Codex CLI 的 `--json` 采集只代表 **CLI 控制实验**。本工具希望证明桌面 Codex 主控的节省效果，就必须另行采集当前桌面会话对应的任务事件与累计 usage 的“终点减起点”，确认规划、最终验收及回退都计入，且期间没有其他任务混入。无法可靠接入桌面数据时，可以报告 DS 真实用量及 CLI 对照结果，**不能声称已经测得桌面 Codex 的节省率**。

`existing-smoke.json`（若存在）是历史链路演示记录：仅有混合组的 DS 用量和公开测试结果，没有完整 Codex 用量及隐藏验收，不进入正式三组比较。本目录未运行付费对照。

```sh
python3 summarize.py runs-template.csv --format markdown
python3 summarize.py runs.csv --format json --output result.json
python3 -m unittest discover -s . -p 'test_summarize.py'
```

## 记录规则

- `task_id`、`repeat`、`arm` 三项构成唯一键；`repeat` 为正整数。汇总器拒绝重复键，避免把一次任务算多次。
- `status` 必填 `pass` / `fail` / `timeout` / `blocked`。其中 `pass` 只是执行结束的自报状态；只有 `pass`、`hidden_pass=true` 且 `human_interventions=0` 才计为已验证成功。隐藏测试必须覆盖全部预先规定的必要要求，不能只测语法。失败、超时和阻塞均保留在分母中。
- `hidden_pass` 与 `usage_complete` 填 `true` / `false` 或留空。`human_interventions` 是超出预先统一允许操作的人工提示、改代码、救场次数；正常输入 API Key 不算介入。未知时留空，不能填 0。
- 所有用量字段未知时留空，JSON 中显示 `null`。**明确没有调用**某类模型时，才给其总输入/输出填 0。`usage_complete=true` 代表所有阶段、修复、回退及隐藏推理用量均已纳入；缺任何阶段就填 `false`。
- `codex_input_tokens` / `ds_input_tokens` 已包含 cached input；`codex_output_tokens` 已包含 reasoning output。缓存和推理两项只是可空的子集，**不能再加一次**。缓存/推理子项缺失不妨碍总量已完整时统计总量。
- Codex 回退的消耗仍记在 `codex_ds_bridge` 原行，不能挪到 `codex_only`。桌面历史 Token 若不能按本次任务准确分离，留空并标记 usage 不完整，不用字数估算冒充实测。
- `usd_cost` 为本次任务所有调用的真实合计费用；缺测留空，不能以跨供应商 Token 直接换算费用。`wall_seconds` 为完整尝试经过的时间，阶段耗时重叠时不能重复相加。
- 模型审查不作为最终真值；使用冻结的隐藏测试、任务必要要求和必要的盲评。试验前写好评分规则；评审不看组名和 Token 数据。

## 怎么读结果

- Codex Token 节省率 = `1 - 混合组全部 Codex(输入+输出) / 纯 Codex 组全部(输入+输出)`。只有任务与重复轮次完整配对、两组 usage 都完整时才计算；否则输出“不可判断”。这个指标不等于订阅额度节省率或人民币节省率。
- 每成功任务用量 = **该组所有尝试的用量（含失败） / 验证成功数**。没有成功或质量/用量缺测时输出 `null`。不要只挑成功任务比较。
- 三组共同任务的成功数、人工介入、时间和费用共同决定是否值得使用。混合组与 `dsh_ds` 的差异是**整套工作流在这批任务上的效果差异**，不能直接推出模型“智力更高”。可选消融组能进一步定位规划模型的贡献。
- 同一个任务重复运行不是独立新任务。本工具不给置信区间或“显著优于”的结论；先看每个任务的配对差异，再扩大到更多独立任务。
- 模板只有表头。单元测试中的数值是清楚标注的人工 fixture，仅验证计算逻辑，不能作为产品效果数据。
